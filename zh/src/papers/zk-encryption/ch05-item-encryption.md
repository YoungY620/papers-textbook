# 攻击二 — 条目级保险库加密

## 保险库并不是单一的密码学对象

用户看到的是一个"安全保险库"，但它并不是单一的密码学对象：条目与用户设置各自存储、各自加密。

如果整个保险库是一个整体，用认证加密（AE）保护就很容易保证完整性：任何一个字节被改动都会被发现。代价在同步——改一个条目名就要重新加密并传输整个保险库。因此三款管理器都逐个条目加密，通常用同一把密钥做 AE。这省掉了同步开销，也丢掉了整体完整性：AE 只保护单个条目，没有任何东西把密文绑定到它所属的条目、它在保险库里的位置、乃至这个保险库本身。条目可以被调换、删除或复制，明文元数据（KDF 迭代次数、用户所属组织）也能被改动，而客户端毫无察觉。

下面所有攻击利用的都是缺失的**保险库完整性**。论文在本类中还报告了 BW04、LP05（Malleable Vault）和 LP06，其描述推迟到完整版。

## 4.2.1 Bitwarden

Bitwarden 对条目和设置的保护并不一致：条目逐个加密，很多设置则完全没有加密，组织内的条目和组织级设置同样如此。一个条目是含若干字段的对象——条目名、密码、用户名、URL——每个字段各自用 AES-CBC-HMAC 加密。2024.2.0 版之前，所有条目的字段直接用用户密钥 $k_u$ 加密；从 v.2024.2.0 起，每个新条目会新采样一把**条目密钥** $k_u^i$ 并用它加密，条目密钥本身再用 $k_u$ 加密后作为条目的另一个字段存放（即图 1 中 item or item key 那一支）。旧条目不会被迁移，因此同一个保险库里两种格式并存；服务器以 JSON 对象返回条目，键是明文字段名，值是相应密文。

### BW05：条目字段交换

没有任何东西把一段密文绑定到某个具体字段。字段名是明文，所有值又都是同一把密钥下的密文，因此攻击者只需在 JSON 的键之间搬移密文：条目名变成密码，密码变成 URL。对采用条目密钥之前的条目，所有字段密文都在 $k_u$ 之下，攻击者还能跨条目调换密文，并用不同条目的字段拼出新条目。该攻击没有交互要求，直接破坏保险库完整性，也是后续攻击的积木。

### BW06：图标 URL 条目解密

条目可以带一个 URL 字段，用于自动填充并显示图标。客户端解密 URL 后向服务器取图标，请求里带上该 URL 的域名和顶级域——URL 为 `https://host.tld/path` 时请求的就是 `host.tld`——于是任何被客户端当作 URL 处理的字段内容都会被攻击者获知。

BW05 补上另一半：把敏感字段（用户名或密码）的密文放进 URL 字段，客户端会把它当成 URL 解密；只要明文满足论文给出的 URL 条件（原文写作"含一个 '.' 且不含 '!'"），图标请求就会把这个秘密带出去。2024 年 7 月上线的 URL 校验和把 URL 的哈希存进另一个加密字段，可以挡住该攻击；但旧条目永远不会补上校验和，只有上线之后创建的条目受保护，而且只有当条目带有条目密钥时才会校验它——攻击 BW10 恰恰能阻止条目密钥被启用。

影响：攻击者可以恢复条目中指定目标的密文，例如用户名或密码。要求：用户打开一个含有未使用条目密钥的条目的保险库（2024 年 7 月之前创建，或在 BW10 执行之后），并且目标明文要满足完整版中给出的附加条件。

### BW07：移除 KDF 迭代次数

客户端认证的做法是：由登录时输入的主密码导出主密钥哈希 $h_m$，服务器把它与存储的哈希比对。由于主密码是唯一的秘密，这个派生被刻意做得很慢：使用基于口令的密钥派生函数（PBKDF），开销由参数决定。PBKDF2 采用默认的 600,000 次迭代时，$k_m \leftarrow \mathrm{PBKDF2}(pw, email, 600000)$、$h_m \leftarrow \mathrm{PBKDF2}(k_m, pw, 1)$；KDF 设置以未加密、未认证的形式存放在服务器上，因此目标用户登录时由攻击者指定参数。把第一次的迭代次数改成 1，工作量就从 600,001 次 PBKDF2 迭代降到 2 次，暴力破解中每次猜测快 300,000 倍。

影响：降低对目标主密码的暴力破解成本，一旦恢复密码即可完全控制该账户。要求：用户登录。

## 4.2.2 LastPass

LastPass 的条目同样由字段构成——条目名、用户名、URL、密码——每个字段都在同一把用户密钥 $k_u$ 下单独加密，因此同类攻击成立。演讲中还有一句旁注：每个字段都用裸 AES-CBC 加密，原则上不好，但在作者的分析中没有单独构成实际攻击。

### LP02：条目字段交换

没有关联数据把密文绑定到字段，所以密文可以在同一条目内部的不同字段之间、不同条目之间调换，也能拼出新条目。

### LP03：图标 URL 条目解密

登录条目可以带 URL，用于自动填充并显示图标；取图标时客户端向 LastPass 的图标服务器发起查询，请求里带上条目内存储的那个 URL——是完整的 URL 本身，而不像 Bitwarden 那样只带域名。用 LP02 把用户名或密码的密文放进 URL 字段，客户端解密后明文就随这次图标查询泄漏出去。与 Bitwarden 不同，这里对明文格式没有任何条件。

影响：攻击者可以恢复条目中指定目标密文的一部分。要求：客户端打开被改过的保险库。

### LP04：移除 KDF 迭代次数

LastPass 的认证会校验由主密码导出的用户密钥哈希与服务器上存储的哈希是否一致。与 Bitwarden 一样需要两次 PBKDF 调用，PBKDF2 默认 600,000 + 1 次迭代；参数同样未加密、未认证，因此由攻击者指定。客户端强制内层最少 2 次迭代、外层固定为 1 次，于是迭代次数可以降到 3 次，暴力破解提速 200,000 倍。

影响与要求同 BW07：降低对目标主密码的暴力破解成本，用户需要登录。

## 4.2.3 Dashlane

Dashlane 把保险库维护成一个事务数据库：每个事务创建、修改或删除一个条目。事务类型和时间戳是未加密的元数据，事务内容则用一把由主密钥和 payload 里的事务参数（KDF 及其参数、密码算法与模式）派生出的密钥加密；盐对所有事务都是固定的。

### DL01：事务重放

事务密钥只取决于这些参数，所以参数相同的事务使用同一把派生密钥，密钥并不唯一地取决于事务本身。服务器因此可以复制、重排或删除事务而客户端察觉不到。这直接破坏保险库完整性，也是 4.4.2 节 Dashlane 一系列攻击的积木——同样的重放会删掉并替换那个保存用户设置的事务。

## 缺失绑定带来的进一步后果

**已知明文预言机装置**（BWb1）出自 Bitwarden 对旧密钥层级的兼容支持。如果服务器在登录响应里把用户密钥密文和私钥密文都置空，客户端会自行生成一对新的 RSA 密钥，并用主密钥 $k_m$ 以 AES-CBC 加密新的私钥后上传。该私钥中包含公钥的编码，于是攻击者得到一组在未知 $k_m$ 下的 5 块明文—密文对。对它做比特翻转，就能伪造出客户端接受的用户密钥密文：BW11 得到 $k_u = k_u^{enc} \| k_u^{mac}$，加密的那一半已知、MAC 的那一半被扰乱，机密性丢失而完整性保留；BW12 只用三块，客户端解析出没有 MAC 部分的密钥并退回 CBC-only 模式，完整性丢失。演讲把这一组攻击称为"Heisenberg 攻击"。BW12 引出的填充预言机只能触达仍处于 CBC-only 模式的条目（带条目密钥的条目仍用 AES-CBC-HMAC），而且论文只把它记为开发者认可其可行性，并未给出可用的 PoC。

**DLb1 填充预言机**来自 Dashlane 的 Flexible 载荷格式仍然接受 CBC-only 加密、且不触发迁移：攻击者借此可以在 $k_{cbc}$ 下解密密文（DLb1）或加密任意明文（DLb2），作者未做优化的实现速度是每块 14 天；DL03 基于 DLb2 注入任意事务。

## 本章要点

- 保险库不是铁板一块：逐条目加密让局部同步廉价，却使整体完整性不再可得。
- 逐条目使用 AE 没有把密文绑定到字段、条目或位置，因此字段、条目乃至整个保险库都能被恶意服务器重组。
- BW05 与 LP02 是基础积木：密文在字段之间搬移，没有条目密钥时还能跨条目搬移并拼成新条目。
- BW06 与 LP03 把这件积木变成机密性泄露：图标请求会带出解密后的条目内容；BW06 要求明文形如 URL 且被 URL 校验和部分挡住，LP03 直接送出存储的 URL。
- BW07 与 LP04 攻击未认证的 KDF 参数而非密文本身，把每次猜测的成本降低约 300,000 倍（Bitwarden）或 200,000 倍（LastPass）。
- DL01 显示 Dashlane 同样失败：事务密钥与事务之间没有绑定，而 BWb1 与 DLb1 把认证缺失变成密钥或明文的恢复。
