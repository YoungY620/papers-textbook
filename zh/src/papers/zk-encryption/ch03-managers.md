# 三款管理器如何加密保险库

用户名、密码、网站 URL：密码管理器把其中的每一项都称为一个条目（item），并把它们统统放进一个保险库（vault）里。会议报告给出的直观图景是：用户只需要记住一个主密码，主密码包裹（wrap）一条保险库密钥，保险库密钥最终加密整个保险库，客户端再把加密后的保险库上传到服务器。报告补充说，保险库并不是一整块经过认证加密的数据：若整体加密，任何一个字段发生变化都要把整个保险库重新加密并重新同步，因此 Dashlane 在条目级别加密，而 LastPass 和 Bitwarden 进一步做到字段级别。这三款产品仍然从同样的两个秘密出发——主密码和邮箱地址——在其上搭出一套密钥层级。

## Bitwarden

### 密钥层级与认证

Bitwarden 用户的密钥层级以主密码和账户邮箱为根，二者分别充当密钥派生函数的输入密钥和盐。KDF 可以是 PBKDF2 或 Argon2id，输出 32 字节的主密钥 $k_m$。认证时客户端发送 $h_m$，即以用户密码为盐、对主密钥再做一次 PBKDF2 迭代的结果，服务器把它与注册时保存的 $h_m$ 比对；报告给出的默认配置是 $k_m \leftarrow \mathrm{PBKDF2}(pw, email, 600000)$ 与 $h_m \leftarrow \mathrm{PBKDF2}(k_m, pw, 1)$。主密钥还通过 HKDF-Expand 以 "enc" 和 "mac" 两个标签派生两条 32 字节密钥，拼接起来即 64 字节的扩展主密钥 $k_{em} = k_{em}^{enc} \| k_{em}^{mac}$。

随后 Bitwarden 均匀随机地采样一条 64 字节的用户密钥 $k_u$。与 $k_{em}$ 类似，它拆成 32 字节的加密密钥 $k_u^{enc}$ 和 32 字节的 MAC 密钥 $k_u^{mac}$。用户密钥是关键：它保护保险库中的全部数据，或者直接加密条目，或者在启用所谓"逐条目密钥"时改为加密那些条目密钥 $k_u^i$，再由后者加密条目字段。用户密钥在 $k_{em}$ 下加密，得到的密文 $c_u$ 存放在服务器上，下次登录时取回。客户端还会生成一对 2048 位模数的 RSA 密钥 $(pk, sk)$，用于下文所述的团队（organisation）；私钥同样在用户密钥下加密后发往服务器。Bitwarden 允许用户和企业自托管服务器，以便完全掌控自己的数据；对自托管实例而言，威胁模型中的敌手就是这台自托管服务器本身。

### 密钥与条目加密

Bitwarden 用 AES-CBC-HMAC 对密钥和保险库条目做认证加密，一条密钥的 "enc" 部分负责加密，"mac" 部分负责 MAC。出于向后兼容，当 "mac" 部分缺失时会省略 HMAC：如果客户端被要求用一条只有 32 字节的密钥加密，就会退回到普通的 AES-CBC。保险库条目的每个数据字段单独加密；字段过去直接用 $k_u$ 加密，但从 2024.2.0 版本起，新条目改用单独采样的逐条目密钥 $k_u^i$，后者再由用户密钥加密，而旧条目仍然直接受 $k_u$ 保护。

### 团队

凭据共享通过团队（organisation）实现。创建团队时客户端采样一条新的 64 字节团队对称密钥 $k_{org}$，并在创建者公钥下加密，得到 $c_{org}^{user}$；同时生成一对团队 RSA 密钥 $(pk_{org}, sk_{org})$ 用于账户恢复，并用 $k_{org}$ 加密团队私钥，得到 $c_{skOrg}$。客户端把 $c_{org}^{user}$、$pk_{org}$ 和 $c_{skOrg}$ 发给服务器；团队中的条目各自用 $k_{org}$ 加密。

创建者通过为受邀者的公钥加密 $k_{org}$ 来添加成员。对每个用户 $user'$，得到的密文 $c_{org}^{user'}$ 存在服务器上，并在同步时下发；受邀者的客户端用自己的私钥解密即可得到 $k_{org}$。因此成员资格是一种能力而非签名名单：客户端能取到 $k_{org}$，就判定该用户属于此团队。团队名称、账户恢复策略等其余数据以明文存放在服务器上，每次同步时下发给客户端。

## LastPass

LastPass 与 Bitwarden 一样从用户密码出发，用 PBKDF2 以邮箱地址为盐派生 32 字节的用户密钥 $k_u$，默认迭代次数为 600,000。认证时客户端发送 $h_u$，即在以密码为盐的条件下对 $k_u$ 再做一次 PBKDF2 迭代的结果，服务器与注册时收到的值比对。用户密钥直接用 AES-CBC 加密保险库条目，完全没有完整性保护。每个用户还有一对 RSA 密钥 $(sk, pk)$；私钥在 $k_u$ 下用 AES-CBC 加密，作为 $c_{sk}$ 与公钥一起存放在服务器上。

LastPass 用户之间的共享通过共享文件夹实现。用户第一次共享条目时，客户端采样一条 32 字节的共享文件夹密钥 $k_{shr}$，再用它以 AES-CBC 加密共享文件夹中的条目。文件夹密钥本身以 RSA-OAEP 对每一位共享对象的公钥加密，于是每个接收者各得到一份密文 $c_{shr}$。

## Dashlane

### 事务与 payload 字符串

Dashlane 把保险库维护成一个事务型数据库。每个事务创建一个、修改一个或删除一个条目；事务类型和时间戳是未加密的元数据字段，事务内容则被加密。内容是压缩后的 XML 数据，记录条目信息或用户设置。由于类型指示（type indicator）和时间戳保持明文，恶意服务器可以重排、重放或丢弃事务，这正是若干完整性攻击的根源。

内容开头的若干字节是一条 payload 字符串，它规定了内容的密码学参数：基于口令的 KDF（PBKDF2、Argon2d，或不派生），它的参数（盐长度、哈希方法以及 PBKDF2 的迭代次数），分组密码（默认 AES-256）与工作模式（默认带 HMAC 的 CBC）。先由口令派生一条 32 字节的中间密钥 $k_{cbc}$；若模式为带 HMAC 的 CBC，再用一次 SHA-512 把它拉伸成 64 字节的 $k_{cbc\text{-}hmac}$。有两种 payload 格式与攻击相关：旧的 KWC3 格式使用 PBKDF2-SHA1 与 AES-256-CBC；Flexible 格式由格式字符串选择 KDF（PBKDF2-SHA256 或 SHA1，或默认的 Argon2d）、分组密码（仅 AES-256）和模式（默认 CBC-HMAC，GCM 是唯一另一种见诸文档的模式）。默认的 PBKDF2 迭代次数是 200,000。用户修改保险库时，客户端创建一个新事务并发往服务器。

### RSA 密钥与共享

每位 Dashlane 用户同样有一对 2048 位模数的 RSA 密钥。私钥以事务的形式加密存放在服务器上，与公钥在一起。这对密钥用于共享：把条目共享给另一位用户（直接共享或在群组中共享）时，采样一条对称密钥 $k_{shr}$，并对接收者的公钥加密，公钥由共享方从服务器取得，结果记为 $c_{shr}$。

## 客户端，以及有多少内容来自文档

这三款目标产品部分是因为其未被混淆的客户端源码可得而被选中：Bitwarden 的源码完整，Dashlane 与 LastPass 只有一部分。概念验证测试只针对 Bitwarden 的网页客户端以及 LastPass 与 Dashlane 的浏览器扩展，因为测试所有客户端的工程量很大；对大多数攻击而言，它们显然是设计问题，与具体客户端无关。在 LastPass 中，浏览器扩展还是唯一支持用于密码重置的"密钥交换"流程的客户端。

对 Dashlane 的描述依据最不充分。它唯一完全开源的客户端是 CLI，而 CLI 既不支持加密也不支持凭据共享，所以此处的描述有一部分来自逆向工程，可能并不完整；与攻击相关的部分则由概念验证加以确认。弄清 Dashlane 与 LastPass 的工作方式，靠的是逆向分析被压缩混淆的客户端 JavaScript 与 Android 应用；此时开放的 Bitwarden 代码已经让作者看清了设计的大致形状。

## 本章要点

- 三款管理器都用基于口令的 KDF 从主密码派生密钥，客户端认证时对该密钥再多做一次 KDF 迭代，并用另一条更长的密钥保护保险库。
- Bitwarden 由 PBKDF2 或 Argon2id 得到的主密钥 $k_m$ 经 HKDF-Expand 派生出 64 字节的扩展主密钥 $k_{em}$，并把随机采样的 64 字节用户密钥 $k_u$ 在其下加密得到 $c_u$。
- Bitwarden 与 LastPass 用 AES-CBC-HMAC 构造加密密钥，其 MAC 部分可能缺失，于是一条 32 字节的密钥会悄悄退回到未经认证的 AES-CBC。
- LastPass 把一条 32 字节的 PBKDF2 输出直接当作保险库密钥配合 AES-CBC，并用一条 32 字节的密钥 $k_{shr}$ 保护共享文件夹，对每个接收者用 RSA-OAEP 包裹。
- Dashlane 把保险库存成事务，事务的类型与时间戳是未加密元数据，内容是以 payload 字符串开头的压缩 XML，后者规定 KDF、分组密码与模式。
- Bitwarden 的团队把成员资格变成一种能力：客户端恰好能在解出 $c_{org}$ 得到 64 字节团队密钥 $k_{org}$ 时才算成员。
- 对 Dashlane 的描述部分来自逆向工程，因为它唯一完全开源的客户端 CLI 既不支持加密也不支持凭据共享。
